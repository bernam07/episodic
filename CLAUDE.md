# Episodic — Project Context

A Letterboxd for television: track series, check off episodes, rate what you finish, follow
what friends watch. Installable PWA, iPhone-first, fully usable on desktop.

Repo: `github.com/bernam07/episodic` (private, MIT).
Status: feature-complete and verified end-to-end against a live Supabase project.
Deployed on Vercel.

---

## Continuing on another machine

```bash
git clone https://github.com/bernam07/episodic.git
cd episodic
npm install
```

**`.env.local` is gitignored and is NOT in this repo.** You must recreate it:

```bash
cp .env.example .env.local
```

Fill it from **Supabase dashboard → Project Settings → API**:

| Variable | Where |
|---|---|
| `VITE_SUPABASE_URL` | Project URL |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Publishable (anon) key |

The publishable key is safe in the client — RLS is what protects data. **Never** put the
Supabase secret key or the TMDB key in a `VITE_*` variable; anything so prefixed is inlined
into the public bundle. The TMDB key lives only in Supabase secrets, server-side.

Then link the CLI to the existing project (the ref is in your dashboard URL):

```bash
supabase login
supabase link --project-ref <PROJECT_REF>
supabase db push        # no-op if already applied
```

Everything is already deployed to the live project — migrations, both Edge Functions, and the
TMDB secret. A fresh machine only needs `.env.local` + `supabase link`. Full setup recipe for a
*brand new* project: [docs/DATABASE.md](docs/DATABASE.md).

## Hard rules

1. **No comments in any source file.** The code must be self-explanatory. The only exception is
   `src/types/database.types.ts`, which is generated by the Supabase CLI.
2. **Clean Architecture, dependencies point inward.** `domain` imports nothing from React or
   Supabase. The UI never imports from `data/supabase` — hooks call use cases, which depend on
   interfaces. `presentation/di/container.ts` is the *only* place concrete implementations get
   bound.
3. **Mobile-first for iPhone**, but must stay usable on desktop.

## Data model — and why

Six tables: `profiles`, `series`, `user_series_status`, `episode_tracking`, `reviews`, `follows`.

**There is deliberately no `episodes` table.** TMDB serves a whole season in one CDN-backed call
and TanStack Query caches it client-side, so mirroring episode content into Postgres would only
add staleness and write amplification. What Postgres stores is episode **counts**
(`series.seasons_meta` JSONB), because progress bars across a whole library must not cost N TMDB
calls. The `user_series_progress` view renders the entire Library screen in one query with zero
TMDB requests. **Do not add an episodes table without revisiting this.**

**Status transitions are automatic.** A trigger on `episode_tracking` (`sync_series_status`)
moves a series to `watching` on first check-in and to `watched` when the last episode is checked
off, reversing on un-check. `abandoned` is never overridden automatically.

**Marking a series "Watched" backfills episodes.** Because only counts are stored, this fetches
every season from TMDB and checks off each **aired** episode (unaired episodes of a returning
series are deliberately left alone). The episodes are written **before** the status, so an
explicit user choice always wins over the trigger — otherwise the trigger would see
aired < total and downgrade it to `watching`. Order matters; don't reorder it.

**Setting a series back to "Want to Watch" clears its check-ins.** `SetSeriesStatus` calls
`clearSeriesEpisodes` for that status, so *want to watch* always means zero progress (no more
"Want to Watch" at 100%). The status sheet warns first. This is the deliberate reverse of the
Watched backfill.

**"Up to date" ≠ "finished".** `domain/entities/Airing.ts` → `describeWatchState` distinguishes
them. A returning series with every aired episode watched is *up to date* (shows next air date);
only an ended series with every episode watched is *finished*. Aired counts derive from TMDB's
`last_episode_to_air` + `seasons_meta`.

**Favorites** are stored as `is_favorite boolean` on `user_series_status`. Toggling uses the
`toggle_favorite(p_series_id)` RPC, which flips the flag (and upserts with `want_to_watch` if
the series isn't in the library yet). Favorites are exposed in `user_series_progress` (own
library) and `get_user_library` (other users' libraries, follow-gated). They appear as a
dedicated "Favorites" filter tab in the Library screen and as a poster grid section on profiles.

## Privacy model

**Libraries are visible only to people you follow.** Enforced in Postgres, not the UI:

```sql
using (
  auth.uid() = user_id
  or exists (select 1 from follows f
             where f.follower_id = auth.uid() and f.following_id = user_series_status.user_id)
)
```

Unfollowing revokes access immediately. Aggregate counts (series/episodes/reviews) are public via
`security definer` RPCs, matching how Letterboxd shows profile stats. Episode-level check-ins stay
private to their owner.

**Username login never exposes emails.** Resolving username → email via a database RPC would leak
every user's email to anyone who can guess a username. It happens inside the **`auth-login` Edge
Function** using the service role instead; the browser only ever receives tokens. The function
returns an identical `invalid_credentials` for both unknown-username and wrong-password, so it
cannot enumerate accounts. `verify_jwt = false` for this function (the user has no token yet) —
this is intentional and must stay.

**Usernames are claimed atomically.** `handle_new_user` raises on duplicates; because it runs
inside the signup transaction, the auth user rolls back too — no orphans. The live availability
check in the UI is convenience, not the guard.

**Deleting your own account** goes through the `delete_own_account()` RPC (`security definer`), which
deletes the `profiles` row and then the `auth.users` row for `auth.uid()`. Everything else — status,
tracking, reviews, follows, and the notifications the user generated for others — cascades via FK
`on delete cascade`. Verified on PGlite that this does **not** hit the FK re-insert trap of bug 3.
The UI (`DeleteAccountSheet`) requires typing your username to confirm, then `AuthProvider` clears
`user`/`profile` and `ProtectedRoute` redirects to `/auth`.

## Notifications

A `notifications` table with two `security definer` triggers:
- `notify_on_follow` — inserts a `follow` row for the followed user.
- `notify_on_review` — inserts a `review` row for each follower of the reviewer (excluding self).

RLS: a user can only select/update their own rows. `get_notifications` returns actor + series data
joined in; `get_unread_notification_count` drives the bell badge on the home header;
`mark_notifications_read` is called when the `NotificationSheet` opens. There is no `/notifications`
route — it is a sheet opened from the bell, same pattern as `EditProfileSheet`.

## Toolchain gotchas (all already hit and resolved)

- **TypeScript 7 removed `baseUrl`.** Paths resolve relative to the tsconfig. Don't re-add it.
- **`erasableSyntaxOnly` is left off `tsconfig.app.json`** (it's only `true` in
  `tsconfig.node.json`, for `vite.config.ts`) — it forbids constructor parameter properties, which
  the DI relies on. esbuild handles them fine.
- **Use `gen_random_uuid()`, never `uuid_generate_v4()`.** Supabase installs `uuid-ossp` into the
  `extensions` schema, which is not on the search path during migrations → `42883`. The migrations
  need **zero Postgres extensions**; keep it that way, or schema-qualify.
- **`[storage.vector] enabled = false`** in `config.toml`. The CLI defaults it on, and pushing that
  to a free-tier project fails with `402 upgrade to a paid tier`.
- `[inbucket]` is deprecated → `[local_smtp]`.
- **TMDB key is a v3 key** (32 hex), not a v4 token. The `tmdb` function detects which it has and
  uses `api_key=` vs `Bearer` accordingly. Either works.
- Tailwind IntelliSense reports `cssConflict` on `bg-x active:bg-y` — false positives, ignore.
  But a genuine conflict class exists: `pt-safe` + `pt-3` on the same element silently clobbers the
  safe-area inset. Use `pt-[calc(env(safe-area-inset-top)+0.75rem)]`.
- **`CREATE OR REPLACE FUNCTION` cannot change a `RETURNS TABLE` column list.** When adding a
  column to a function's return type, use `DROP FUNCTION ... ; CREATE FUNCTION ...` instead. This
  bit `get_profile_summary` (adding `bio`) and `get_user_library` (adding `is_favorite`).
- **Supabase CLI in Codespaces**: `supabase login` requires a TTY. Use
  `export SUPABASE_ACCESS_TOKEN=<token>` then `npx supabase db push`.

## Bugs already fixed — do not reintroduce

1. `uuid_generate_v4()` → `gen_random_uuid()` (extension not resolvable).
2. `gin_trgm_ops` index needing `pg_trgm` — dropped entirely; search goes through TMDB, so a local
   fuzzy index was dead weight.
3. **Deleting a user silently failed.** The `sync_series_status` trigger fired on cascade-delete of
   `episode_tracking` and tried to re-insert a `user_series_status` row for the already-deleted
   profile → FK violation → whole delete aborted, dashboard button did nothing. Fixed in
   `20260716120400` by bailing when the profile is gone and never inserting on DELETE.
4. **"Watched" didn't mark episodes.** `setStatus` only wrote one row. Fixed with
   `CollectAiredEpisodes` + `set_series_watched` RPC (see Data model above).
5. **Desktop horizontal overflow**: `main` had `w-full` *plus* a 240px sidebar margin → 1680px in a
   1440px window. The sidebar offset lives on a wrapper's padding now.
6. `pt-safe` + `pt-3` conflict on the home header.
7. `"1 people you follow"` pluralisation — fixed with shared `pluralize()` utility.

## Supabase Storage

**Bucket: `avatars`** — public, 5 MB limit, `image/jpeg`, `image/png`, `image/webp` only.

Each user's avatar is stored at `{userId}/avatar` (no extension, `upsert: true`). This fixed
path means re-uploading overwrites the same object — no orphaned files. The public URL is
cache-busted by appending `?t=Date.now()` to the URL stored in `profiles.avatar_url`, so every
upload is seen by all viewers on next profile fetch.

RLS on `storage.objects`:
- Select: all authenticated users (avatars are public).
- Insert/update/delete: own folder only (`(storage.foldername(name))[1] = auth.uid()::text`).

## Verification approach

No Docker, so schema work is verified against **PGlite** (Postgres compiled to WASM) with the
Supabase bits shimmed in, *before* pushing. The shim must include:

```sql
create schema auth;
create role anon; create role authenticated; create role service_role;
create table auth.users (id uuid primary key, email text, raw_user_meta_data jsonb, ...);
create function auth.uid() returns uuid ... current_setting('request.jwt.claim.sub', true);
grant usage on schema auth to anon, authenticated, service_role;
grant execute on function auth.uid() to anon, authenticated, service_role;
```

That last grant matters — without it, `security invoker` functions calling `auth.uid()` fail with
`permission denied for schema auth`, which is a shim artifact, not a real bug. Also **do not add
extensions to the shim**: PGlite installs them into `public`, which masks the very
`extensions`-schema problem that breaks real Supabase.

UI is driven with **Playwright** (Chromium) at iPhone 15 Pro / iPad Pro / 1440px desktop, against
`npm run preview`, using two real accounts that follow each other.

**Tests now live in the repo** under `tests/` and run with **Vitest** (`npm test`) — 74 tests:
- `tests/*.test.ts` — pure-function units (airing/watch-state, rating/username/email/avatar
  validators, plural, initials, releaseYear, hasAired) and the `SetSeriesStatus` orchestration
  (watched backfills, want_to_watch resets, episodes-before-status ordering) with fake repos.
- `tests/schema.test.ts` — the schema/RLS/social/notification/delete/hardening checks against real
  Postgres via **PGlite**, using the shared harness in `tests/support/pglite.ts` (`createMigratedDb`
  applies all migrations under the shim). Runs in CI — no browser, no live backend.

`tests/` is outside `src`, so `tsc -b` does not type-check it; Vitest transpiles via esbuild.
`vitest.config.ts` is standalone (does **not** load `vite.config.ts`, to avoid the PWA plugin) and
re-declares the `@` alias.

**Playwright smoke** (`tests/e2e/*.spec.ts`, `npm run test:e2e`) is an **unauthenticated** shell test
(boots, redirects to `/auth`, form renders, PWA manifest, no overflow, no console errors). It creates
no accounts, so it does not pollute the live project. `playwright.config.ts` forces **Chromium** on
both the mobile (iPhone 15 Pro viewport) and desktop projects — the iPhone device descriptor defaults
to WebKit, which is not installed; override with `browserName: "chromium"`. It is **local-only**, not
in CI (it needs a build with real `.env.local` for the Supabase client to construct).

**CI** (`.github/workflows/ci.yml`) runs `typecheck → test → build` on every push and PR (Node 24,
`npm ci`). This exists specifically to catch the "committed a broken build / unpushed migration"
failures that have happened twice across machines. The build needs no secrets: `vite.config.ts`
falls back to `""` for missing `VITE_*` vars (`env.VITE_… ?? ""`), so it compiles in CI. The
lockfile carries the full cross-platform rollup binary set, so `npm ci` resolves on Linux even
though it was generated on Windows.

Trap when writing the PGlite schema tests on a **shared** db: RLS `select count(*)` returns rows the
viewer can see including **their own**, so a follow-gating check must count the *other* user's rows
(`where user_id = $bob`), not all visible rows. Blocks that assert on `follows`/`notifications` clean
those tables in their own `beforeAll` — Vitest does not guarantee cross-`describe` execution order.

⚠️ **Schema (PGlite) and UI (Playwright) checks are still scratchpad-only** and not in the repo. The
PGlite shim for schema work must grant usage on the `auth` schema and stub `storage.foldername(text)
returns text[]` (used by the avatars-bucket RLS), and must **not** install extensions. Porting these
into `tests/` (needs a DB harness / a preview-server fixture) is still open.

Recurring trap when writing Playwright checks: **strict-mode violations read as failures.**
`text=Library` matches both a heading and the nav tab; `"Watching"` matches Abandoned's
description *"Stopped watching…"*. Use `getByRole` with an exact/regex name. Always check the
screenshot before believing a red result.

## Key UI features

- **Auth landing page**: Poster-wall backdrop from trending series, feature highlights, auth form.
  Two-column layout on desktop (poster wall left, form right).
- **Episode detail**: Tap any episode row → bottom sheet with still image, formatted air date,
  runtime, TMDB rating, full description, mark-watched toggle.
- **Cast rail**: Horizontal scroll of circular actor photos + name + character on series detail.
  Data from `/series/:id/credits` edge function route (top 20).
- **Profile editing**: EditProfileSheet — avatar upload (tap avatar, hidden file input), display
  name, bio (160 chars with counter). Followers/following lists via FollowListSheet (tap counts).
- **Favorites**: Heart toggle on series detail, "Favorites" tab in Library, poster grid on profiles.
- **Library filter persistence**: Filter state stored in URL search params (`?status=watching`).
  Navigating to series detail and pressing Back restores the active filter. Profile stat tiles
  deep-link to the correct library filter.
- **Notifications**: Bell on the home header with an unread badge, opening `NotificationSheet`
  (follow + review activity). Marked read on open.
- **Delete account**: Danger action at the bottom of the profile; `DeleteAccountSheet` gates it
  behind typing the username, then signs out and redirects to `/auth`.
